# 自建收信找回密码计划

> 2026-11-10 方案更新：用户已选择 QQ 邮箱 `2639548777@qq.com` + IMAP 自动读取，替代下文自建 SMTP 网关的部署部分；不需要 MX 或入站 25 端口。邮件仍独立验证 DKIM，账号申请和改密流程保留。部署与真实收信验证说明位于后端仓库 `docs/password-reset-imap.md`。

> 执行方式：使用 executing-plans 按步骤执行，每一步检查工作区、实现、验证、CR、单独提交。本文是跨服务的方案与实施分解；当前仅检查了前端仓库，后端文件路径、依赖和部署配置须在实施第一步核实，不能把本文当成已经验证可部署的后端代码。

**Goal:** 用户从账号登记邮箱主动发信，自建服务验证邮件后自动更新密码；系统不向用户发信，不要求所有注册用户先验证邮箱。

**Architecture:** 自建专用 SMTP 收信网关，接收单一地址，完成邮件来源认证并可靠入队；同机后台任务通过现有账号服务执行重置。网页生成一次性申请并暂存新密码的哈希，邮件携带申请编号，核验通过后才使新密码生效。

**Tech Stack:** 当前前端为 Vue 3、Vue I18n、Vite、Vitest；收信层建议采用 Postfix + Rspamd，复用现有后端框架、数据库、密码哈希和会话撤销机制。组件选型需结合服务器现有软件核实，不自动安装依赖。

## 一、范围与决策

- 使用自己的域名和服务器，不注册第三方邮箱，不建设完整邮箱系统。
- 不实现出站邮件、邮箱网页、IMAP、附件处理，也不改注册流程。
- 接收地址使用专用子域名，例如 `reset@account.example.com`。`example.com` 是文档示例，不是实际部署域名。
- 邮箱登记错误或无法使用时，展示人工申诉 QQ：**2639548777**。
- 登记邮箱控制权是找回依据，接受用户使用他人邮箱注册所承担的风险。
- 不使用统一默认密码 `123456`。建议用户在网页填写新密码，后端只暂存哈希，收到有效邮件才更新账号；这项交互是本计划的建议，尚未实施。
- 不把新密码、密码哈希、登录 token 放进邮件或日志。
- 不抽取现有认证模块，不重写登录和注册，不新增页面路由；在现有登录区域增加找回面板，保留当前导航行为。

## 二、“检验发信邮箱”具体指什么

只判断邮件里的 `From` 等于登记邮箱不够：客户端可以自行填写这个字段。SMTP 的 `MAIL FROM` 也不是邮箱所有权证明。

第一版采用较保守的自动处理条件：

1. `From` 必须能解析为唯一邮箱地址，且与目标账号当前登记邮箱匹配；沿用现有账号邮箱匹配规则，不自行删除点号、加号或改写本地部分。
2. 收信网关验证 DKIM 签名通过，签名覆盖 `From` 和包含申请编号的完整邮件正文；拒绝只签部分正文的 DKIM `l=` 形式。
3. 通过验证的 DKIM 签名域与 `From` 域按照 DMARC 的域对齐规则对齐；核验由成熟组件完成，不自行实现密码学或域名后缀判断。
4. 对本身不签名、签名损坏或无法确认来源的邮件，不自动重置，网页说明可联系 QQ 申诉。DNS 等临时故障暂缓处理，不能当成通过。
5. 不信任外部来信自行携带的 `Authentication-Results` 或自定义“验证通过”头。网关移除冒充本地认证来源的头，处理任务只读取网关生成的可信认证元数据。

DKIM 证明域名授权签发了邮件；对具体邮箱地址的信任还依赖发信服务商正确限制用户冒用其他地址。它不是对人的绝对身份认证。上线前用实际 QQ 邮箱及主要用户邮箱测试其发件身份约束和签名情况，不能宣称所有邮箱都一定可自动找回。

## 三、用户流程与最小接口

1. 用户点击“忘记密码”，`showConfirm` 说明使用登记邮箱发信、邮件处理后新密码才生效，以及 QQ 申诉方式。
2. 用户填写登记邮箱和新密码，向建议新增的 `POST /api/auth/password-reset/requests` 提交 `{ email, new_password }`，通过 HTTPS 传输。
3. 后端执行现有密码强度校验，生成至少 128 位不可预测申请编号，记录编号哈希、用户标识、新密码哈希、创建和到期时间、申请时的账号凭据版本以及处理状态。有效期建议 30 分钟。
4. 无论账号是否存在，均返回相同结构的 `{ request_id, expires_in: 1800 }` 和通用说明；不存在的账号不关联可重置用户。限制 IP 与目标邮箱的申请频率，并限制待处理记录总量。
5. 网页显示收件地址和邮件模板，提供分别复制收件地址、复制模板及 `mailto:` 按钮；剪贴板失败时保留可手动选择的文本，不强制跳转邮件应用。
6. 用户必须从登记邮箱直接发送，第一版不支持他人代发或转发。模板只含固定主题和申请编号：

   ```text
   主题：密码找回申请

   RESET-REQUEST: <网站生成的申请编号>
   ```

7. 收信网关先完成来源核验与持久化，再交给后台任务匹配申请；任务事务内检查登记邮箱未改变、账号凭据版本未改变、未过期、未处理。
8. 检查通过后更新密码，撤销旧会话，消耗当前申请并使同账号其他待处理申请失效。用户返回原登录表单，用自己刚才填写的新密码登录。
9. 第一版不增加状态查询接口或自动登录。网页明确说明可能存在邮件延迟、申请期限及失败后的 QQ 申诉方式。

账号存在性不能通过错误提示或明显不同的响应路径直接泄露。创建新申请不撤销旧密码，也不立即废除其他未完成申请，避免他人反复发起申请阻止本人找回。

## 四、收信服务边界

- 域名 DNS：收信主机 A 记录、专用收信子域名 MX 记录；仅在 IPv6 实际可用时发布 AAAA。不覆盖主域名原有邮箱配置。
- 网络：确认公网入站 TCP 25 可达；只开放接收指定本地域名及地址，禁止邮件中继。支持 STARTTLS，使用正常维护的服务端证书。
- 邮件认证：成熟网关完成 DKIM 和域对齐校验，设置 DNS 查询超时；不因为验证组件不可用而放行重置。
- 接收限制：建议最大邮件 256 KiB，限制连接与投递频率；仅解析文本正文，不执行 HTML、不打开附件、不访问邮件中的 URL。
- 可靠性：使用 SMTP 队列及持久化交接；必须在可靠存储邮件后才返回成功接收。后端暂时不可用时重试，重启不能丢失已接受申请。
- 内部交接：同机 Unix socket 或权限受限的本地队列，避免新增公网重置回调接口；账号密码只能经现有后端业务函数更新，收信程序不直接改数据库密码字段。
- 幂等：以申请记录的事务状态为依据，不依赖可伪造的 `Message-ID`；重复投递和并发处理都只能成功一次。
- 运维：复用服务器现有进程管理，配置自动重启、队列磁盘上限和日志轮转。仅记录处理结果与内部追踪标识，敏感原文不进入普通日志，待处理哈希和邮件按短期保留策略清理。
